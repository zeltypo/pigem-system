## 1. System Architecture at a Glance (100% Cloud-Hosted)

The system consists of three layers that work together without changing the ISP's final approval authority (**Human-in-the-Loop**):

1. **Frontend Layer (`web/html/*.html`, `web/style.css`, `web/js/*.js` on Vercel Static Hosting):**
   - **Public Website & Application Form (`index.html`, `about.html`, `apply.html`, `apply.js`):**
     - Displays Fiber Plans (`Plan 1000`, `Plan 1400`, `Plan 1900`), interactive **Leaflet.js Cavite installation map** with reverse geocoding, early **non-blocking client-side ID quality warnings** (`checkLocalImageQuality`), **Desktop-to-Phone QR Code ID Upload**, and **Google reCAPTCHA v2**.
   - **Customer Portal (`customer.html`, `customer.js`, `activate.html`, `login.js`):**
     - 6-digit email activation with `Send / Resend Code`, simplified 3-stage customer status tracker (**Processing**, **Approved**, **Rejected**), and a targeted **Needs Correction** resubmission form with **Desktop-to-Phone QR Code Upload** (`openCustQrUploadModal`).
   - **Agent Portal (`agent.html`, `agent.js`):**
     - Displays applications with **Green / Yellow / Red** AI triage badges, separates **Application Details** from **AI Screening & ID Review**, renders **OpenCV.js cropped & enhanced ID previews** (preserving upright portrait IDs in preview and download), and lets the Agent either request a correction (with GPT-5.4 polite remark assistance) or confirm & forward to the Manager.
   - **Manager Portal (`manager.html`, `manager.js`):**
     - Reviews Agent-verified applications (`Ready for Provider Encoding`), records the ISP provider reference number and encoding proof, and sets final status (`Approved`, `Installed`, `Rejected`).
   - **Admin Console (`admin.html`, `admin.js`, `#admin-setup`):**
     - Provisioned once using the 48-character hex `admin_setup_code` generated by `schema.sql`. Creates verified Agent/Manager credentials, toggles the `ai_enabled` master switch, monitors the background screening queue, and manages plans/CMS content.

2. **Serverless Python Backend (`api/*.py` on Vercel Python Runtime):**
   - **[api/index.py](file:///c:/pigem-system/pigem-system-duplicate/api/index.py):** FastAPI router handling `/api/health`, `/api/verify-captcha`, `/api/screen/queue`, `/api/screen/worker`, `/api/screen`, `/api/notify`, and `/api/polite-remark`.
   - **[api/_quality.py](file:///c:/pigem-system/pigem-system-duplicate/api/_quality.py):** **Stage 1 Image Quality Gate** — computes local OpenCV sharpness/brightness/glare metrics and runs a **stateless `gpt-6.2-sol`** inspection to route the ID into **Route A (`good`)**, **Route B (`fixable`)**, or **Route C (`bad`)** and choose which OpenCV actions to apply.
   - **[api/_preprocess.py](file:///c:/pigem-system/pigem-system-duplicate/api/_preprocess.py):** **Stage 2 Targeted OpenCV Enhancement** — 100% deterministic OpenCV pixel processing (`deskew_crop`, `clahe`, `sharpen`, `deglare`, `brighten`, `denoise`, and orientation rotation). **Portrait IDs stay portrait**, and AI never alters pixels.
   - **[api/_idp.py](file:///c:/pigem-system/pigem-system-duplicate/api/_idp.py):** **Stage 3 Identity OCR** — calls **Azure AI Document Intelligence** (`prebuilt-idDocument` + `prebuilt-read`) on the OpenCV-prepared Front and Back ID photos.
   - **[api/_ai.py](file:///c:/pigem-system/pigem-system-duplicate/api/_ai.py):** **Stage 4 Deterministic Validation & `gpt-5.4` Triage** — compares extracted Name, Birth Date, ID Number, and ID Type against applicant inputs using deterministic Python rules, assigns **Green / Yellow / Red** triage, and uses **stateless `gpt-5.4`** to draft clear Agent queue summaries and customer correction guidance.
   - **[api/_screening_queue.py](file:///c:/pigem-system/pigem-system-duplicate/api/_screening_queue.py):** Durable background queue worker triggered immediately on submission and every minute by Supabase `pg_cron`.
   - **[api/_mailer.py](file:///c:/pigem-system/pigem-system-duplicate/api/_mailer.py):** Dual-port Gmail SMTP client (Port 465 SSL + Port 587 STARTTLS fallback) compliant with the Data Privacy Act of 2012 (RA 10173).

3. **Database, Private Auth & Multi-Bucket Storage (`Supabase PostgreSQL + Storage`):**
   - **13 Public Tables (`public.*`):** `users`, `plans`, `system_settings`, `website_content`, `agent_links`, `applications`, `documents`, `screenings`, `corrections`, `provider_updates`, `notifications`, `login_history`, `system_logs`.
   - **4 Private Security & Queue Tables (`pigem_private.*`):** `screening_staff` (bcrypt password hashes + 2-hour session tokens), `admin_setup` (one-time SHA-256 setup code), `screening_intake` (single-use CAPTCHA intake tickets), and `screening_jobs` (durable background screening queue).
   - **11 Document Storage Buckets (`documents` + `documents-1`..`documents-10`):** Automatic multi-bucket failover in [web/js/db.js](file:///c:/pigem-system/pigem-system-duplicate/web/js/db.js) (`dbUploadDocument`) and [api/_screening_queue.py](file:///c:/pigem-system/pigem-system-duplicate/api/_screening_queue.py) (`download_raw_photo`) so uploads automatically spill over to the next bucket if a bucket is full.

## 2. The 4-Stage Conditional AI + OpenCV + Azure DI Pipeline (Step-by-Step)

When an applicant submits an application (or resubmits a `Needs Correction` form):

1. **Stage 1 — Image Quality Gate (`api/_quality.py` -> `gpt-6.2-sol`):**
   - First computes fast OpenCV metrics (`laplacian_var` for blur, `mean_brightness`, `glare_ratio`, `contrast_std`, and SHA-256 hash check for duplicate front/back uploads).
   - Calls `gpt-6.2-sol` in a **fresh stateless request** (`previous_response_id=""`, `store_response=False`) with an explicit **Anti-Hallucination Rule** and **Orientation Rule** (upright portrait IDs have `rotation_degrees = 0`).
   - Classifies the upload into one of 3 routes:
     - **Route A (`good`):** Image is clear and readable.
     - **Route B (`fixable`):** Image is tilted, slightly dark, or has minor glare/blur that OpenCV can improve.
     - **Route C (`bad`):** Image is severely blurry, wrong document type, or duplicate Front/Back.

2. **Stage 2 — 100% OpenCV Targeted Preprocessing (`api/_preprocess.py`):**
   - Executes only the OpenCV actions planned by Stage 1 (`rotate_*`, `deskew_crop`, `deglare`, `brighten`, `clahe`, `denoise`, `sharpen`).
   - `detect_card_quad` uses multi-pass Canny edge detection + Adaptive Threshold + ConvexHull (`1.12 <= aspect <= 2.35`) so both **portrait and landscape** Front and Back IDs crop accurately while keeping portrait IDs upright.

3. **Stage 3 — Azure Document Intelligence OCR (`api/_idp.py`):**
   - Sends the OpenCV-enhanced working copies to Azure Document Intelligence (`prebuilt-idDocument` and `prebuilt-read`) to extract structured fields (`FirstName`, `LastName`, `DateOfBirth`, `DocumentNumber`) and raw printed text lines.

4. **Stage 4 — Deterministic Field Comparison & `gpt-5.4` Triage (`api/_ai.py`):**
   - Python deterministic rules compare the applicant's form data (`full_name`, `birth_date`, `id_number`, `id_type`) against the OCR extraction.
   - Assigns deterministic triage:
     - **GREEN (`Ready for Agent Confirmation`):** Good quality + all fields match.
     - **YELLOW (`Needs Agent Verification`):** Minor name/middle-initial variation or partial OCR read.
     - **RED (`Recommended for Correction — Agent Review`):** Unreadable ID, duplicate front/back, wrong ID type, or major field mismatch.
   - Calls `gpt-5.4` in a stateless call to generate the plain-language `queue_summary` for the Agent and `final_recommendation` for the correction note.

## 3. Top Oral Defense Panel Questions & Best Answers

### Q1: "Does the AI modify the applicant's ID photo or automatically reject applications?"
**Answer:**
No. First, **100% of pixel modifications are performed by deterministic OpenCV algorithms** (`api/_preprocess.py`: 4-point perspective crop, CLAHE contrast enhancement, gamma brightening, deglare, and unsharp mask sharpening) on a working copy—the AI models (`gpt-6.2-sol` and `gpt-5.4`) never alter or generate pixels, and the customer's original upload is preserved. Second, the system follows a strict **Human-in-the-Loop** design: even when an application is flagged **Red** or **Yellow**, the AI only provides preliminary findings and pre-fills a suggested correction message. A human **Agent** must always review and click confirm before any status change occurs.

### Q2: "Why did you use two different OpenAI models (`gpt-6.2-sol` and `gpt-5.4`) plus Azure Document Intelligence and OpenCV?"
**Answer:**
Each tool handles the specific task it is best at:
- **`gpt-6.2-sol` (Stage 1 Quality Gate)** inspects visual quality and plans which OpenCV filters are needed.
- **OpenCV (Stage 2)** performs deterministic geometric card cropping and contrast/sharpness enhancement while preserving portrait or landscape orientation.
- **Azure Document Intelligence (Stage 3)** provides specialized OCR (`prebuilt-idDocument` + `prebuilt-read`) purpose-built for extracting printed text and dates from identity cards.
- **Python Deterministic Rules + `gpt-5.4` (Stage 4)** compare the extracted text against the applicant's entered form fields and write polite, human-readable guidance for the Agent and Customer.

### Q3: "How did you prevent the AI from hallucinating when multiple IDs are uploaded?"
**Answer:**
We enforced two safeguards:
1. **Stateless Execution (`previous_response_id=""`, `store_response=False`):** Every single ID screening request runs in a completely isolated, stateless API call so context from a previous applicant or previous upload can never leak into the next evaluation.
2. **Explicit Anti-Hallucination Prompt Constraints:** Both `gpt-6.2-sol` and `gpt-5.4` receive strict system instructions to evaluate only the visible pixels and verified OCR JSON of the current upload and never invent text or defects.

### Q4: "What happens if a user uploads a blurry photo or if the primary Supabase storage bucket becomes full?"
**Answer:**
- **Non-Blocking Early Warning:** On the frontend (`apply.js` and `customer.js`), `checkLocalImageQuality()` immediately warns the user if a photo looks blurry, dark, or glaring, but **does not block them** from re-uploading or submitting—Stage 1 and Stage 2 on the server will still attempt targeted OpenCV enhancement.
- **11-Bucket Automatic Storage Failover:** In `web/js/db.js`, `dbUploadDocument()` iterates through `DOCUMENT_BUCKETS` (`documents` and `documents-1` through `documents-10`). If the primary bucket is full or errors, it automatically fails over to the next bucket without interrupting the applicant.
